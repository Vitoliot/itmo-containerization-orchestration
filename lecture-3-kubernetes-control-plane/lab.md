# Лабораторная 3 — собрать платформу для `shop`

Это локальный план реализации задания 3. Полная формулировка и порядок
проверок приведены в [эталонном задании курса](https://github.com/KeladKaal/containerization-and-orchestration/blob/main-rus/lecture-3-kubernetes-control-plane/lab.md).

## Что должно быть реализовано

1. **Сервисы.** `api` с `/health`, `/order`, `/orders` и `worker`, который
   обрабатывает заказы через PostgreSQL.
2. **Политики кластера.** Выбрать Kyverno или Gatekeeper, описать не менее
   пяти правил и подготовить пять негативных манифестов, каждый из которых
   нарушает отдельное правило.
3. **Helm-чарт.** Добавить `Chart.yaml`, `values.yaml`, шаблоны Deployment и
   Service для `api` и `worker`, пробы, лимиты, метки и настройки реплик.
4. **Reconciliation.** Проверить восстановление удалённого Pod, изменение
   числа реплик, rolling update, зависший rollout с плохой readiness-пробой и
   rollback.
5. **PostgreSQL через оператор.** Подключить один оператор на кластер и
   описать объект CRD в чарте; сравнить его reconciliation с
   `controller-manager`.
6. **Падение control plane.** Зафиксировать недоступность операций управления и
   продолжение работы `api`, `worker` и PostgreSQL, затем восстановить кластер.
7. **Мониторинг.** Добавить `ServiceMonitor`/`PrometheusRule`, выбрать и
   обосновать три алерта, показать хотя бы один firing.

## Критерии готовности

- чарт устанавливается без отклонений политиками;
- удалённые Pod возвращаются автоматически;
- успешное и сломанное обновления различаются readiness-проверкой;
- rollback возвращает рабочую ревизию;
- объект PostgreSQL восстанавливается оператором;
- приложение отвечает при остановленном control plane;
- мониторинг использует существующий стек, а не поднимает отдельную копию.

Скриншоты и логи проверок должны храниться в `screenshots/` и ссылаться из
итогового README после выполнения лабораторной.
