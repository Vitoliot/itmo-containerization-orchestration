# Skill: анализ неудачной CI-сборки

## Назначение

Сформировать доказательный Markdown-отчёт о неудачном запуске GitHub Actions, не выполняя исправлений и не изменяя внешние системы.

## Порядок действий

1. Проверить наличие `owner`, `repo`, `run_id` и `head_sha` во входных данных.
2. Вызвать `actions_get` с методом `get_workflow_run` и зафиксировать статус, conclusion, событие, ветку и URL запуска.
3. Вызвать `get_job_logs` с `failed_only=true`, `return_content=true` и ограничить результат последними 200 строками.
4. Вызвать `get_commit` с `detail=stats`, чтобы определить изменённые файлы без загрузки полного patch.
5. Через `search_files` найти в `/data` runbook по устойчивому фрагменту ошибки, затем прочитать подходящий файл через `read_text_file`.
6. Сопоставить изменённые пути с `service-owners.md`.
7. Сформировать отчёт по обязательному шаблону.

## Правила

- Считать фактом только данные, полученные из входного webhook или инструментов.
- Для каждого факта указывать источник: GitHub Actions, commit или конкретный runbook.
- Любой вывод модели помечать как гипотезу и указывать уровень уверенности: низкий, средний или высокий.
- Не запрашивать полный patch, если статистики изменённых файлов достаточно.
- Не раскрывать значения секретов и не повторять потенциальные секреты из логов.
- Не выполнять rerun, commit, изменение файлов или настроек репозитория.
- Предлагать исправление только тогда, когда оно описано в runbook и признаки совпадают.
- Для неизвестной ошибки рекомендовать ручную диагностику и эскалацию владельцу.

## Обязательные разделы отчёта

1. `# Отчёт о сбое CI`
2. `## Подтверждённые факты`
3. `## Гипотезы`
4. `## Рекомендуемые действия`
5. `## Владелец и эскалация`
6. `## Источники`
